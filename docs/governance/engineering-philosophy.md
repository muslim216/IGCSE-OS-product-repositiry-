# Engineering Philosophy

> **Governance layer.** The principles that decide cases no rule covers.
>
> **Status:** Active · Part of Engineering Constitution v1.1
>
> **Authority:** Tier 1. Where a specific rule and a principle here appear to conflict, the
> specific rule wins for the case it names — but a rule that repeatedly conflicts with a
> principle is evidence the rule is wrong. See `governance/documentation-authority.md`.

Rules cover the cases someone anticipated. This document covers the rest. When you face a
decision the constitution does not name — and you will, often — these are the priorities
that decide it.

They are ordered. Where two principles pull in opposite directions, the earlier one wins.

---

## 1. Explainability over opacity

Every number MANARA shows must be able to say where it came from. This is not a
nice-to-have: it is the product. A tutor who cannot see why a student's readiness moved
cannot act on it, cannot defend it to a parent, and will not trust it a second time.

Concretely, this is why the Readiness Engine is deterministic weighted evidence rather than
a model, why `factor_evaluations` is an append-only row per factor per run rather than a
JSON blob on a snapshot, why `evaluation_run_id` ties a score to its exact inputs, and why
an AI is asked for a score and a rationale but never for a grade.

Prefer a simpler mechanism you can explain to a better one you cannot.

## 2. Human authority over AI automation

The tutor is the authority. Every AI output is a proposal until a human accepts it or an
explicitly-defined, narrowly-scoped trust rule accepts it on the tutor's behalf.

Where automation acts without a human — auto-finalized marks are the one place it does —
the conditions must be written down, conservative, and observable. Auto-finalize requires
both an official mark scheme and model confidence of `high` or `medium`; everything else
waits in a queue. That boundary is a product decision, not an implementation detail, and
moving it is an architectural change.

A tutor can always override, and every override is recorded in an append-only audit row
with no API to edit or delete it.

## 3. Student trust is a product feature

Students submit photographs of their own handwriting to a system that marks them. That is
an act of trust, and the product's job is to deserve it.

This is why a student can contest any finalized mark and why that request is never resolved
by AI — it routes to the tutor with the model's original reasoning attached. It is why
self-declared data is labelled as self-declared rather than presented as observed. It is
why missing data reads "not enough data yet" instead of zero: a fabricated zero tells a
student they failed something they never attempted.

When a change would make the system more efficient but less trustworthy, it is the wrong
change.

## 4. Fail safely

Degrade, do not collapse. A missing API key makes one surface report a clear "not
configured" state while the rest of the app runs. A failed AI synthesis keeps the
deterministic factor rows it already computed and writes `status="failed"` rather than
losing the evaluation. A readiness subject with no v2 snapshot falls back to v1 and says so
in the response rather than rendering a blank page.

The pattern generalizes: when a dependency fails, preserve the work already done, tell the
user precisely what is unavailable, and keep everything else working.

## 5. Explicit systems over hidden magic

Prefer the mechanism a reader can see. Jobs are rows in a table you can query, not messages
in a broker you cannot. Prompts live in one versioned registry, not scattered through the
services that call them. Migrations are hand-written and numbered, not autogenerated.

Magic is fast to write and expensive to debug at 3am. When you must be clever, write down
why in a comment or an ADR — this codebase's comments explain *why*, and that norm is worth
more than the code it annotates.

## 6. Simplicity over cleverness

The best solution is the one the next engineer understands without asking. Two-thirds of
this system's leverage comes from a small number of deliberately boring choices: one
database, one deployable API, integer primary keys, a polling worker.

A clever abstraction that saves fifty lines and costs an hour of comprehension is a bad
trade. So is a general solution to a problem we have exactly one instance of.

## 7. Maintainability before premature optimization

Write the clear version. Measure. Then optimize the part that is actually slow, and leave a
comment saying what you measured.

The exceptions are the ones that are cheap now and expensive later: an index on a column you
know will be filtered, a query that is obviously N+1, an AI call inside a loop. Those are not
premature — they are design.

Cost counts as performance here. A burst of submissions collapsing into one synthesis call
rather than one per submission is a performance decision measured in dollars, not
milliseconds.

## 8. Build systems engineers enjoy maintaining

A codebase is a place people work. Tests that run in seconds without a database, a local
setup that is three commands, errors that say what went wrong, and documentation that is
true — these are not luxuries, they are what keeps the system alive after the person who
built it moves on.

If a task is miserable every time, that is a defect report about the system, not about the
person doing it.

## How to use this document

When a decision is not covered by a rule:

1. Find the earliest principle above that clearly applies.
2. Decide.
3. If the decision was hard, or will bind future work, write an ADR
   (`docs/adr/README.md`) so the next person inherits the reasoning rather than
   re-deriving it.
4. If the same decision comes up a third time, it wants a rule. Propose one through
   `governance/change-process.md`.

## Review triggers

- A principle is repeatedly overridden by specific rules — it is either wrong or badly
  worded.
- The product's trust model changes (for example, a new class of AI output acting without
  a human).
- A new principle is proposed and accepted through the change process.
